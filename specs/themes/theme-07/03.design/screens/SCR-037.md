### v1.3.4 — UIF-07 context override

Trong UIF-07, screen hiển thị source-authorized return, supplier/source/warehouse và Product+LOT+pending quantity. Source version change trước handover được hệ thống tự phản ánh; không có manual state/release CTA. UIF-09/UIF-10 không thay đổi.

### v1.3.6 — UIF-07 physical-preparation override

Trong `UIF-07`, screen được render với title **Chuẩn bị hàng trả** và sở hữu một task riêng: user đối chiếu Product, quantity và LOT trên hàng vật lý đang chuẩn bị. Mỗi item phải được xác nhận trước khi sang `SCR-039`; scan LOT là hỗ trợ, không bắt buộc Phase 1.

Nếu source version thay đổi trước handover:
- hiển thị delta cụ thể, ví dụ `8 → 5; bỏ 3`;
- affected item bị reset physical verification;
- server vẫn authoritative và user không thể override hard guard.

UIF-09/UIF-10 giữ context contract cũ.

### UIF-07 override v1.3.9 — Physical preparation

- Group theo Product+UOM; mỗi group có 1..N LOT allocations. Cùng Product khác UOM là item riêng.
- Source Product/UOM/LOT/quantity là read-only; không nhập quantity lần hai.
- Mỗi allocation có physical verification riêng. Scan/typed LOT optional; LOT khác source là blocker, không silent substitution.
- `Không khớp thực tế` khóa final review; warehouse không tự giảm quantity/đổi LOT. Source owner phải amendment.
- Source update chỉ reset affected allocation; unaffected verified evidence giữ nguyên. Source remove/cancel được system release.
- Leave/resume giữ verification nếu source không đổi.

### v1.4.1 — Inventory Operations holistic UX correction

- Product header không lặp tracking tail (`N LOT` / `Không theo lô`) khi allocation rows đã thể hiện cấu trúc.
- Normal unverified allocation không lặp badge `Cần kiểm`; badge chỉ giữ cho verified/affected/mismatch states có giá trị phân biệt.
- Verification dùng standard `VBottomSheet`, không custom close icon; LOT input và helper được rút gọn.
- Source quantity vẫn read-only; mismatch/source amendment rules không đổi.

### v1.4.2 — Semantic hierarchy & task affordance

- `UIF-07` hiển thị hierarchy **Product+UOM parent → allocation child** bằng composition khác nhau; Product và LOT không được cùng visual weight.
- LOT allocation child có semantic label `Lô cần kiểm`; non-LOT allocation dùng `Phần hàng cần kiểm`.
- Normal unverified row không spam badge nhưng phải có action hint nhẹ `Kiểm` + chevron. Remove redundant communication, not necessary communication.
- Progress copy dùng `N/M đã kiểm`, dựa vào visible child hierarchy thay cho từ `mục` mơ hồ.
- Verification Bottom Sheet tách rõ `Sản phẩm` và `Lô cần khớp`. Input scan/type được label **`Quét hoặc nhập LOT để đối chiếu`**, kèm guardrail `không thay đổi LOT của yêu cầu`; không còn affordance giống edit LOT.

### v1.6.0 Inventory Audit & Control context

### v2.9.1 — UIF07 preparation hierarchy correction

- Request context alone uses canonical `Status / Compact` List Row.
- Product+UOM is a structural `VSection` heading (`VText + VBadge`) so the product parent is visually distinct from LOT/allocation children. It is not a List Row/card.
- Allocation children use uniform `Navigation / Default` List Rows, one exact source allocation per row.
- Default allocation copy avoids repeating low-value labels such as “Chưa kiểm”; only abnormal/completed status is surfaced when useful.

### v2.9.2 — Product grouping surface correction

- Supersedes the v2.9.1 raw `VSection + VText + VBadge` parent. Product+UOM is a canonical `List Row / Status / Compact` within one bordered surface; allocation LOT/non-LOT children remain `Navigation / Default` rows.
- This deliberately uses an existing DS primitive rather than a custom header composition. Product and LOT remain visually distinct through density, trailing semantics and parent surface hierarchy.

### v2.9.3 — Grouped-collection correction

- Supersedes the v2.9.2 per-Product bordered surface. `Hàng cần chuẩn bị` has one light grouped surface following Figma Layout `4518:1545`.
- Product+UOM is exact `List Row / Status / Compact` (`525:519`, `370×52`); each actionable allocation is exact `List Row / Navigation / Default` (`370×76`). Product subgroups have no independent border/background/card treatment.
- Verification sheet uses semantic Product status and an `Info Row` for required quantity; no raw quantity badge.

### v3.9.5 — Source-slice & physical-observation contract

- Each allocation is keyed by stable `source_line_id/source_allocation_id`; Product/UOM/LOT/quantity remain source-authoritative.
- Exact original-state source slices are server-owned facts. If only one valid composition exists the system auto-resolves it. If multiple stock-state compositions are valid, the verification sheet progressively exposes **Xác định nguồn tồn** and requires exact per-state quantities summing to the source allocation.
- `Không khớp` no longer stores a boolean only. It opens a short `VBottomSheet` for `QUANTITY | LOT | ITEM_NOT_FOUND | OTHER`; actual quantity/LOT are captured conditionally, `OTHER` requires note, actor/time are system-recorded. No photo is mandatory in Phase 1.
- Submitting a physical observation has no stock effect and makes the request read-only until Purchase/source emits a new version. New source version resets only affected allocation verification and preserves unaffected source-slice/verification evidence.
